---
name: figma-inspect-map
description: Extract the selected Figma frame and map design nodes to verified O11 components during a figma-to-o11 run.
---

Inputs are the validated config, run ID, Figma read access and scoped Test Module inventory. Read the selected node only. Discover context, metadata, screenshot, component and variable tools from the connected Figma server. If a verified revision is known, run `reuse <config> <run> <view> <revision>` first. A hit restores the manifest and PNG. With no trustworthy revision, acquire them afresh.

Obtain hierarchy, frame dimensions, variants/states, instance IDs and names, Auto Layout, constraints, fills, text styles and weights, borders, radii, shadows, assets and available variables. Expand individual child nodes only when necessary. Write the minimal selected-node document with actual Figma field names and node IDs. Save real PNG bytes from the server export or screenshot at the documented scale. Avoid using generated JSX as a design manifest. For vector paths/images retain the node ID, the approved local asset file and its intended O11 resource. Record component metadata, resolved variable values, unknowns and adaptation assumptions in run-local design notes keyed by node ID. See [evidence formats](../../../setup-docs/harness-evidence.md).

Run `import <config> <run> <view> <node.json> <reference.png> [revision]`. If MCP cannot supply structured design or downloadable pixels and REST fallback is enabled, use `rest <config> <run> <view>` with the operator-supplied FIGMA_ACCESS_TOKEN in the environment. If the design changed during capture, repeat the acquisition. Stop on a missing primary reference. Inspect responsive variants from their own assigned frame URLs. For a viewport without a variant, record the adaptation assumptions and run the available responsive checks.

Read only the matching module style's upstream UI references. Verify native widgets, referenced OSUI patterns and available project blocks/styles against the Test Module. Populate inventory.json from these reads. Use the canonical config/osui-registry.json. Use native primitives for controls and the matching consumed OSUI or project block for a composite. Read the effective theme chain and applicable screen/block sheets. Fill the attempt theme evidence and the per-view model plan before mapping. Reuse existing classes and theme tokens. Only add scoped CSS or a token after verifying the capability is absent and recording the specific gap. Prefer a reusable block for repeated complex instances. Never author inline CSS, including widget CustomStyle, a style extended attribute, literal HTML style, or script-written inline declarations. Express dynamic states with classes. Keep the widget tree lean. Justify any fallback, map supported properties, pairing and state, and resolve unsupported mappings explicitly in the inventory or registry. Run `map <config> <run> <view>` for each design frame. Deliver the manifest, reference, mapping and screen plan. Stop on unresolved dependencies or user decisions.
